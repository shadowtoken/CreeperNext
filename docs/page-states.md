# 页面状态与交互反馈规范

页面质量不仅是正常状态的截图。每个异步区域应考虑加载、成功但无内容、失败、正常内容；每个写操作应考虑空闲、提交中、失败、成功。先按真实场景实现，不为了状态齐全添加假业务或全局状态框架。

## 现有基础组件

| 能力 | 位置 | 约定 |
| --- | --- | --- |
| 区域加载 / 空内容 / 错误 | `components/shared/content-state.tsx` | 标题、可选说明和明确操作；页面自己持有 main 和布局 |
| 表单错误 / 成功 | `components/ui/feedback.tsx` | 原地反馈；错误 alert，成功 status；不展示后端原始错误 |
| 提交反馈 | `components/ui/button.tsx` | pending + pendingLabel，自动 disabled / aria-busy，独立礼貌播报 |
| 认证重复提交锁 | `features/auth/lib/use-submission.ts` | 同一帧重复触发也只开始一次请求；不是服务端幂等替代品 |
| 认证错误分类 | `features/auth/lib/auth-failure.ts` | 白名单文案、明确字段、恢复动作；不传播后端 message |
| 认证恢复操作 | `features/auth/components/auth-recovery-action.tsx` | 过期返回登录，已在其他页面完成设置则主动刷新状态 |
| 路由错误 | `app/error.tsx` | 使用当前 Next 的 retry 重新请求，可返回首页 |
| 根布局错误 | `app/global-error.tsx` | 自带 html/body 和基础样式，不依赖已失败的 Provider |
| 404 | `app/not-found.tsx` | 明确地址不存在与返回入口；与业务空列表语义不同 |
| 账户加载 | `app/(protected)/account/loading.tsx` | 位于受保护布局内，不替代或绕过服务端门禁 |

这些组件不强制使用某个 UI 库，可以替换外观，但要保留交互语义与可访问性。颜色使用现有语义 Token；无需新加 Toast、Spinner 或动效依赖。

## 读取状态

- 首次读取：在实际异步边界使用 `loading.tsx` 或局部 Suspense。能预测布局时做匹配骨架，不能预测时使用简短加载说明；不加虚假百分比、固定等待时间或永远转圈的动画。
- 空内容：请求成功且确实无数据时才显示。按场景区分“尚未创建”和“筛选无结果”，给出创建或清除筛选的操作。不要用空态掩盖网络错误、无权限或后端异常。
- 刷新已有内容：保留旧内容和上下文，局部标记更新状态；不要每次整页替换为 loading。
- 失败：明确未完成的动作与下一步。不要渲染堆栈、SQL、Token 或未经筛选的 `error.message`。
- 404 使用 Next 的 `notFound()` / `not-found.tsx` 语义，不是正常返回空数组。共用展示组件不意味着共用 HTTP 状态。

账户 loading 不覆盖同级/父级布局，因此不承诺在权限检查等待期间立刻出现。不要为了展示 loading 移除授权门禁或在根部随意加入 Suspense：响应流一旦开始，后续 redirect/404 可能不能再改变 HTTP 状态码。

```tsx
// 在实际业务区域内，使用真实状态和真实操作，不强制添加示例路由。
<ContentState
  kind="empty"
  title="没有符合条件的内容"
  description="试试减少筛选条件。"
  action={<Button onClick={clearFilters}>清除筛选</Button>}
/>
```

## 写操作

1. 校验输入后开始请求，立即锁定同一操作。按钮显示具体动作，例如“正在保存…”，而不是无意义的“Loading”。
2. 不禁用整张页面；只锁当前提交和会与它冲突的操作。例如 TOTP 验证期间不能重新生成二维码。
3. 失败后恢复按钮、保留输入、显示原地提示；允许用户修改并重试。预期的业务失败由返回值处理；网络异常必须 catch，错误边界不会替你处理事件回调中的异常。
4. 成功留在当前页面时明确确认结果，需要时清空敏感输入。成功跳转时保持 pending 到组件卸载，避免导航间隙再次提交。
5. 创建、付款等写操作不做隐式自动重试；UI 防重复不等于服务端幂等控制。

### 提交中的输入契约

登录、注册、验证码、绑定验证器及修改密码在 pending 期间将本次提交的输入设为 `readOnly`，防止界面内容与请求快照不一致。失败后解除只读，保留原值以便修改重试；成功跳转前保持锁定。不要用整个 disabled fieldset 替代它：只读输入仍可聚焦、选择、复制，且保留 FormData 字段。

密码显隐不修改输入内容，提交中仍可使用；输入本身 disabled 时，显隐按钮同步禁用。多个密码字段的按钮分别标注“显示密码”“显示确认密码”“显示当前密码”等，不能让读屏用户猜测控制的是哪个字段。明文显示时也关闭拼写检查、自动纠正和首字母大写。邮箱采用同样的输入配置；末字段使用 `enterKeyHint="done"` 提示移动键盘，不拦截浏览器默认的 Enter 提交。

保持按钮的独立加载播报，不在整张 form 上叠加 `aria-busy` 来延迟其内部 live region。客户端只读和提交锁属于交互约束，不替代服务端校验、权限检查或幂等控制。

认证错误按原因处理：

- 网络错误和 5xx：表单级提示，保留输入，不把所有字段标红。HTTP 故障优先于响应体中的字段错误码。
- 429：提示操作频繁；只有明确的 `ACCOUNT_TEMPORARILY_LOCKED` 才称为账户锁定，不推测锁定时长。
- 明确字段错误：例如 `INVALID_PASSWORD` 在改密表单只关联当前密码，在绑定表单只关联确认密码；`INVALID_CODE` 只关联动态代码。
- 本地校验：空白称呼、密码确认不一致时不请求接口，渲染错误后聚焦对应输入。原生 required/type/minLength 校验继续保留。
- 验证过期：提供带有安全 returnTo 的返回登录入口，停止提交同一个失效操作。不会自动退出、清除 Cookie 或重发写请求。
- 已在其他页面完成绑定：显示真实的“刷新状态”操作，重新经过服务端门禁；不要只写“正在刷新”却不执行，也不要由客户端自行授予登录权限。
- 未知错误码：使用该操作的通用安全提示，不猜测邮箱是否已注册，不展示数据库/服务端原文。

```tsx
<Feedback error={error} errorId="save-error" success={message} />
<Button type="submit" pending={pending} pendingLabel="正在保存…">保存</Button>
```

基础 Button 默认 `type="button"`，表单提交显式写 `type="submit"`。普通 disabled 使用禁止操作光标，pending 才表示等待。底层组件不请求接口，业务层拥有异步生命周期。

## 可访问性与响应式

- Feedback 的空 live region 始终存在，结果更新后再播报，不叠加父级 aria-live。错误文字通过 `aria-describedby` 与有关输入关联；字段校验失败使用 `aria-invalid`。
- 字段标记只来自本地校验或已知的服务端错误码，网络失败不表示每个字段都填错。当前实现是小型认证域错误适配，不是通用表单框架；新增业务在自己的 Feature 维护映射，UI 原子不认识 Better Auth 错误码。
- 不自动移动所有反馈的焦点；多字段校验可聚焦第一个非法输入，路由标题与错误摘要按实际交互管理焦点。输入焦点、文本和滚动位置不能因加载状态反复丢失。
- 成功信息不要瞬间消失，关键失败不要只放 Toast；长文案自然换行，操作区允许换行，触控目标至少 44×44。
- 状态不依赖颜色或动画表达；验证浅色/深色、窄屏、200% 文本与 reduced-motion。不宣称自动化测试能代替真实读屏器检查。

## 验收

`tests/browser/states.spec.ts` 在手机和紧凑桌面验证慢请求、同帧重复提交、服务端失败、断网、保留输入、失败后重试、注册成功提示、退出失败留在原页以及 404 在 200% 文本下的布局。现有 onboarding 测试继续验证真实注册→TOTP→改密成功链路。

认证增强测试还覆盖本地错误焦点、改密字段定位、429 与账户锁定区别、失效验证码停止重试、恢复链接，以及实际在另一操作中完成 TOTP 后刷新到受保护账户。`pnpm test:auth-ui` 独立验证错误码和 HTTP 状态映射、不泄露响应原文，不依赖数据库。

运行 `pnpm db:test:up` 后执行 `pnpm test:responsive`。测试中被拦截的请求仅用于验证 UI 状态，不替代真实 HTTP/数据库测试；后者由 `pnpm test` 执行。路由异常重试、加载流式过程和真实 VoiceOver 播报仍需发布前人工验收。
